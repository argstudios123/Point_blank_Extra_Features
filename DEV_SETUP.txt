1. Use Java 17.
2. Open this folder as the Forge 1.20.1 project.
3. The VPB 2.2.0 development dependency is in libs/.
4. Run `gradlew genIntellijRuns` or the equivalent IDE setup task if needed.
5. Run the client from the generated Forge run configuration.
6. Do NOT copy the VPB JAR into the final published Point Blank Extra Features JAR.
7. Point Blank itself must be installed separately at runtime.

Note on running from the IDE (dev environment):

1. Mixin config registration
   Forge 1.20.1 registers mixin configs through the JAR MANIFEST "MixinConfigs"
   attribute read by Mixin's MixinPlatformAgentDefault. The "[[mixins]]" block in
   mods.toml is a NeoForge-only feature and is ignored by Forge 1.20.1, so a mod
   that only declares it there silently loads NO mixins (no error, no crash - the
   mixins simply never apply).
   In a dev run the mod is a directory rather than a jar, and Mixin reads
   "<mod root>/META-INF/MANIFEST.MF" for that directory. That is why this project
   ships src/main/resources/META-INF/MANIFEST.MF containing:
       MixinConfigs: pointblankextra.mixins.json
   Do not delete it: without it neither ClientEventHandlerMixin (toggle aiming)
   nor GunItemMeleeControllerMixin (melee animation controller) is applied.
   The `jar` task in build.gradle sets the same attribute for the published jar.

2. Dependency mixin refmaps
   Point Blank 2.2.0 and GeckoLib 4.8.4 ship "searge"-only mixin refmaps.
   fg.deobf() remaps their classes but not their refmaps, so the
   `remapDependencyRefmaps` Gradle task patches the refmaps in the deobfuscated
   dependency jars. It scans every deobf jar that contains a *.refmap.json
   (matching by file name is not reliable: ForgeGradle names curse.maven
   artefacts e.g. "vics-point-blank-961053-...", which does not contain the
   substring "pointblank"). It is wired as a dependency of runClient/runServer
   and runs automatically; you can also run it manually with
   `gradlew remapDependencyRefmaps`.

3. Weapon JSON (addon-specific keys)
   The addon reads its extra keys from the same weapon JSON Point Blank uses and
   ignores everything else, so Point Blank's behaviour is unchanged.
       "toggle_aiming": true          // top-level boolean (also accepts "enabled"/"true")
       "features": [                  // an existing Point Blank array
         { "type": "Melee", "enabled": true, "damage": 10.0, "cooldown": 20,
           "reach": 3.0,
           "damageCatsandOcalotsEntities": false,
           "meleeAnimations": [
             { "name": "animation.model.melee_1", "duration": 780, "preMelee": 150 },
             { "name": "animation.model.melee_2", "duration": 780, "preMelee": 150 },
             { "name": "animation.model.melee_3", "duration": 780, "preMelee": 150 }
           ] }
       ]
   "damageCatsandOcalotsEntities" (boolean, default false) - whether THIS melee
   feature may damage cats and ocelots. The key is spelled exactly as written and
   must not be "corrected"; a JSON without the key counts as false, so adding the
   key never changes anything but this one behaviour.
       true  - cats and ocelots take the configured melee damage normally
       false - cats and ocelots take no melee damage; the swing, its animation, the
               animation-time preMelee impact, the cooldown, the reach and the
               damage dealt to every other entity are all unchanged, and the target
               ray cast still picks a cat/ocelot exactly as before (only the damage
               is skipped, so no damage can land on another entity instead)
   It is honoured only by the melee feature: Point Blank's bullets, explosions and
   other weapon damage are untouched.
   Unit conventions (both mirror Point Blank's own weapon JSONs, where every
   animation-time value is milliseconds - e.g. inspectAnimations 9180 ms == the
   baked animation's 9.1833 s length, and GunItem computes a baked length as
   Math.round(animation.length() * 50.0) ms):
       "duration" - how long the animation keeps playing, in MILLISECONDS of
                    animation time. 0/omitted means "no window", i.e. GeckoLib
                    plays the animation's own baked length.
       "preMelee" - the animation time, in MILLISECONDS, at which the hit is
                    applied. It is NOT a Minecraft-tick delay and it is not
                    converted to ticks: V is pressed -> a random configured
                    animation starts immediately -> the addon tracks the position
                    of that playing animation -> the moment it reaches `preMelee`
                    the damage/reach/knockback hit is applied -> the animation
                    keeps playing until its duration has passed.
                    "preMelee" delays the hit, never the animation.
   How the animation time is read: GeckoLib's animation clock is real time, not
   the world tick counter (RenderUtils.getCurrentTick() == Blaze3D.getTime() * 20.0,
   i.e. 20 animation ticks per real second, so 1 animation tick == 50 ms). The
   melee controller reports the position GeckoLib samples the rendered pose with
   (AnimationController#adjustTick) and the addon compares that against
   `preMelee` / `duration`. A paused game does not advance it, animation speed
   does, and neither the world's tick counter nor an extra timer is involved.
   The client therefore decides *when* the animation has reached `preMelee` and
   tells the server; the server still validates and applies the hit, and owns
   damage, reach, cooldown and target selection.
   The legacy shape "animations": [ "animation.model.melee_1", ... ] (a plain array
   of names, no animation times) is still accepted.
   Weapon extensions live in run/pointblank/<Extension>/ with the usual Point
   Blank layout, i.e. assets/pointblank/items/<weapon>.json.
   On every resource reload the addon logs one line per weapon that has extra
   features enabled, e.g.:
       Point Blank Extra Features: loaded 'aw_an94'
           (toggleAiming=true, melee=enabled[damage=8.0, cooldown=20, reach=3.0,
            damageCatsandOcalotsEntities=false,
            animations=[animation.model.melee_1[duration=780ms, preMelee=150ms], ...]])
   and one line per swing, which is the quickest way to confirm the timing:
       Melee animation 'animation.model.melee_1' started on controller 'extra_melee'
           (hit at animation time 150.0 ms, window 780.0 ms)
       Melee 'animation.model.melee_1' reached its impact at animation time 152.3 ms
           (preMelee 150.0 ms)
       Melee 'animation.model.melee_1' played its whole 780.0 ms window (784.4 ms);
           stopping the controller
   and, instead of the "Melee hit target ..." line, a line per swing that landed on a
   cat or ocelot while "damageCatsandOcalotsEntities" is false:
       Melee attack on cat/ocelot target 8842 dealt no damage:
           "damageCatsandOcalotsEntities" is false for this weapon
   The impact line reports the animation time the hit was fired at, so it should
   sit just past `preMelee` (one rendered frame of overshoot at most).
   If that line is missing for a weapon, the JSON was not found or not parsed.

   ADS behaviour keys (all optional; Point Blank ignores them, only the addon
   reads them, and every one of them defaults to the pre-existing behaviour):
       "noADSDuringInspect": true       // top-level boolean, default false
           While the weapon is being inspected, ADS is released immediately and
           new ADS activation is blocked until the inspection ends. The release
           is Point Blank's own exit (setAiming(false) + AimingChangeRequestPacket)
           so no half-cleared aim/sprint state is left behind.

       "disableAdsDuringreload": true   // top-level boolean, default false.
           The spelling (lower-case "reload") is intentional and part of the
           format; do not "correct" it.
           While the weapon is reloading, ADS is released immediately and new ADS
           activation is blocked for the whole reload (prepare, the reload itself,
           its cooldowns, results and iterations - GunClientState#isReloading()
           covers all of them), so pressing/holding/spamming ADS cannot re-enable
           it. As soon as the reload ends ADS is available again and is never
           re-entered automatically. Works with normal, empty, phased and
           iterated reloads, and coexists with toggle_aiming and
           noADSDuringInspect.

       { "type": "AdsConstraint", "enabled": true, "camera": true,
         "cameraConstraint": 0.8 }      // inside "features"
           cameraConstraint (number, optional, in [0, 1]) is the RETAINED fraction
           of the first-person camera movement while ADS, applied uniformly to
           Point Blank's "_camera_" bone: 1.0 keeps all camera movement (no
           constraint), 0.8 keeps 80%, 0.5 keeps 50%, 0.0 fully constrains it.
           It only affects the camera; the weapon root ("main") keeps using the
           per-axis fractions from the model's "constraint" bone as before. When
           the key is absent the camera keeps the previous behaviour (the same
           per-axis fractions as the root), so old JSONs are unchanged.

       { "type": "AdsReloadZoomControl", "enabled": true,
         "zoom_type": "smooth", "amount": 0.09 }   // inside "features"
           Temporarily relaxes the ADS zoom while reloading, relative to the
           weapon's current ADS zoom (nothing is hardcoded). amount is the
           fraction relaxed at full transition (0.0 = no effect ... 0.2 = strong).
           zoom_type shapes the transition and is exactly one of: linear, smooth
           (default), ease_in, ease_out, ease_in_out, sine_in, sine_out,
           sine_in_out. A missing or invalid zoom_type falls back to smooth.
           The relaxation begins when the current reload starts and eases over a
           fixed 200 ms window (the old transition length), measured from the
           start of the current reload - not the total reload duration. From then
           until the reload finishes the reduced zoom is held, and when the reload
           ends the normal ADS zoom is smoothly restored. It adapts to reloads of
           any length/type (normal, empty, phased, iterated). The transition is
           eased, never a snap: Point Blank's own zoomValue RealtimeLinearEaser
           (200 ms, in ClientEventHandler#onFovUpdate) smooths both the ramp and
           the restore. The feature touches only the zoom value - never _camera_,
           constraint bones, animation JSON or tracks - and is independent of
           AdsConstraint.

4. Melee animation controller name (do not rename it)
   The melee animation is played by a dedicated GeckoLib controller named
   "extra_melee" (MeleeConstants.MELEE_CONTROLLER). Point Blank does not blend like
   vanilla GeckoLib: BlendingAnimationProcessor#tickAnimation collects, per bone,
   what every "default layer" controller produced into a HashMap keyed by
   "_default:" + controller name, then keeps exactly one entry - the first one in
   HashMap iteration order whose controller is RUNNING (a later RUNNING controller
   only beats an earlier non-RUNNING one). HashMap order follows
   String.hashCode(), so the controller NAME decides who wins.
   Point Blank's own default-layer controllers sit in buckets 3..11
   (overheat_controller 3, fire_controller/hide_controller 4, draw_controller 7,
   inspect_controller 8, complete_fire_controller 9, enable_fire_mode_controller 10,
   idle_controller 11); "extra_melee" sits in bucket 0 for every realistic map
   capacity, so the melee pose always wins the bones it animates while it plays.
   This is load-bearing: animation.model.melee_* animate the same bones
   (main, leftarm, rightarm) as animation.model.idle, and with the previous name
   ("pbextra_melee", bucket 12) Point Blank's idle controller was visited first and
   silently threw the melee pose away - GeckoLib reported the animation as playing
   but nothing was visible in first person.
   Nothing of Point Blank's is patched or overridden: when the melee animation ends
   the "extra_melee" controller simply stops producing pose data and Point Blank's
   own idle/fire/draw/reload controllers take the pose back over on their own.


5. Where a melee swing may trigger (Point Blank weapon state)
   A swing only starts while Point Blank's own weapon state for the gun that would
   play the animation is a normal idle state and the player is not sprinting. The
   state comes from Point Blank's existing state object, read through its public
   accessors - GunClientState#getMainHeldState when the key is pressed,
   #getMainHandState / #getOffhandState for the granted swing - which resolve the
   very same OperableGunContext the melee feature uses. No parallel state system is
   tracked; the state checked is always the state of the weapon that would animate.
       allowed : IDLE, PREPARE_IDLE, IDLE_COOLDOWN (idle or walking - walking is a
                 pose overlay in Point Blank, not a weapon state), dual wielding
                 with that weapon idle
       ignored : DRAW (drawing/equipping), aiming on, FIRE_* and COMPLETE_FIRE
                 (shooting, including its cooldowns), every PREPARE_RELOAD/RELOAD/
                 COMPLETE_RELOAD state, INSPECT, CHANGE_FIRE_MODE, OVERHEAT,
                 HIDING/HIDDEN (holstering), and sprinting
   An ignored press does nothing at all: nothing is requested, no animation plays,
   no hit is dealt and no cooldown is consumed, so the running Point Blank action is
   never interrupted, cancelled or overridden. The check runs twice - when the key is
   pressed and again immediately before the melee animation starts (a Point Blank
   action can begin during the request round trip) - and a rejection logs one debug
   line, e.g.:
       Melee input ignored: the weapon is reloading
